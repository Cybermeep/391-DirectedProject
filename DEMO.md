# Demo Runbook

This walks through presenting the project live: real attacker-shaped
traffic from other machines, picked up by the NIDS, producing alerts with
ML confidence and a generated explanation, plus a guaranteed fallback
path that doesn't depend on live capture working perfectly on demo day.

**Everything here targets machines you own on your own LAN.** See
`demo/_safety.py` for the hard-coded guardrails (private-IP-only,
packet/rate/duration caps) built into every script.

## 1. Topology

- **Machine A ("NIDS host")**: runs the Flask backend (with packet
  capture) and the frontend. This is the machine you present from.
- **Machine B, C ("attackers")**: your other two Windows machines, or
  just two more terminals on Machine A if you'd rather not deal with a
  physical LAN. Either works - the scripts just need to reach Machine
  A's IP.

If using separate terminals on one PC instead of separate machines,
target `127.0.0.1` and capture on your loopback interface (`Npcap
Loopback Adapter` on Windows, `lo` on Linux) instead of your real NIC.

## 2. Before the demo (once)

```bash
# On Machine A
python installer/setup_wizard.py --model-dir /path/to/your/trained-model-folder
cd backend && ./venv/bin/python run_api.py     # Windows: venv\Scripts\python.exe run_api.py
```

In a second terminal on Machine A:
```bash
cd frontend && npm install && npm run dev
```

Open the app, register an account (or use Google sign-in if configured),
and log in.

**Find Machine A's LAN IP** (`ipconfig` on Windows / `ip addr` on
Linux/macOS) - you'll pass this to the attacker scripts as `target`.

**Find the right capture interface**: in the dashboard, the interface
picker calls `/api/capture/interfaces`. On Windows this lists Npcap-named
adapters (not "eth0") - pick the one matching your active network
adapter. Capturing on Windows generally requires running the backend as
Administrator.

**Start a target listener** so the attack/benign scripts have something
real to hit:
```bash
# On Machine A, third terminal
python demo/target_listener.py --port 8899
```

**Start capture** from the dashboard UI (or `POST /api/capture/start`
with the interface name).

## 3. Live attack demo

From Machine B (or a second terminal on Machine A):

```bash
cd tempStore/demo

# Port scan
python port_scan.py <Machine-A-IP> --start-port 1 --end-port 200 --i-own-this-network

# SYN flood
python syn_flood.py <Machine-A-IP> --port 8899 --i-own-this-network
```

From Machine C (or a third terminal):
```bash
# Ordinary traffic, for contrast - dashboard should stay quiet during this
python demo/benign_traffic.py <Machine-A-IP> --port 8899 --i-own-this-network --count 15
```

Watch the dashboard: alerts should appear in real time as flows complete
or as built-in signatures cross their threshold.

### Two independent detection paths - know which one you're demoing

This matters for how you narrate the demo, so it's worth being precise:

- **Built-in signatures** (`rules/rate_signatures.py`, the "Signature
  Detection" table on the dashboard) count events **across many packets/
  flows** from one source IP within a sliding time window - e.g. "100
  SYNs in 10 seconds." This is what actually catches `port_scan.py`
  (distinct destination ports from one source) and is *always* what
  catches `syn_flood.py`, regardless of anything else.
- **Custom AST rules** (the Rule Builder page, e.g.
  `SYN_Flag_Cnt > 5 AND RST_Flag_Cnt > 3 AND Flow_Byts/s > 1000`)
  evaluate **one completed flow at a time**. `demo/syn_flood.py` uses a
  fixed source port for its whole run specifically so all its packets
  land in a single flow - this means if you've saved a custom rule like
  the example above via the Rule Builder *before* running it, that rule
  will also fire, alongside the built-in signature. `demo/port_scan.py`
  touches a different destination port with every packet by design, so
  each one is its own single-packet flow - a custom AST rule can't
  meaningfully catch a scan shaped this way; only the built-in
  distinct-port-count signature can. Don't expect a custom rule to fire
  during the port scan script - that's expected, not a bug.
- `demo/predict_showcase.py` bypasses live capture entirely and is the
  most reliable way to show the **ML model's** confidence and reasoning,
  independent of either mechanism above.
- **Attack type / rule matched** (if it tripped your SYN-flood rule from
  the Rule Builder) or **ML-detected anomaly** (if the model flagged it)
- **Confidence** (`ml_confidence` field)
- **Explanation** (generated by `explainability/explanation_generator.py`)

### Being upfront about the live path

Say this out loud during the demo, it's good practice and also true:
live flow-feature computation (`ml_pipeline/live_features.py`) is a
best-effort reconstruction of the CICFlowMeter-style schema the model was
trained on - not a byte-for-byte match to the original tool. The **rule
engine** result is exact and fully reliable (you control the thresholds).
The **ML confidence number** from live traffic is illustrative rather
than a lab-validated accuracy figure. See `AUDIT.md` for the full
writeup.

## 4. Guaranteed fallback / opening act: `predict_showcase.py`

This doesn't depend on packet capture, LAN topology, or Npcap at all - it
talks straight to the already-running backend's REST API with realistic,
hand-built feature vectors representative of the attack classes the
model was trained on (CSE-CIC-IDS2018). Good as either your primary demo
of "the ML model's reasoning" or your safety net if live capture misbehaves
mid-presentation.

```bash
cd demo
python predict_showcase.py --api http://localhost:5000/api
```

This will, in order, print its progress for:
1. Registering/logging into a demo account
2. Upgrading it to Enterprise with a dummy test card (proves the billing
   flow)
3. Creating the example SYN-flood rule via the rule builder API (proves
   the AST parser/validator end-to-end)
4. Three predictions - SYN flood shape, port scan shape, and an ordinary
   HTTPS session - each printing **prediction, confidence, and the
   explainability module's generated explanation**, and raising real
   alerts on the dashboard for the two attack-shaped ones

## 5. Suggested demo order

1. Show the login screen, register/sign in with Google.
2. Show the Upgrade screen, upgrade to Enterprise with a test card.
3. Show the Rule Builder: paste the example rule, point out the live
   validation and the field whitelist, save it.
4. Run `predict_showcase.py` - narrate the prediction/confidence/
   explanation output as it prints, then show the resulting alerts on
   the dashboard.
5. Run the live attacker scripts from another machine/terminal, showing
   alerts arriving in real time via WebSocket.
6. (Optional) Run `benign_traffic.py` to show the dashboard staying calm
   during ordinary traffic.

## Troubleshooting

- **No alerts at all from live capture**: check `/api/capture/status` -
  confirm `is_capturing: true` and `active_flows`/`flows_processed` are
  increasing. If `flows_processed` increases but no alerts appear, your
  traffic simply isn't tripping the rule or the model's threshold -
  that's expected for very short demo bursts; lean on
  `predict_showcase.py`.
- **"Permission denied" starting capture on Windows**: run the backend
  as Administrator (Npcap requires it for raw capture).
- **Scapy scripts fail to send packets**: same Npcap/admin requirement
  applies to the attacker scripts themselves.
- **`/api/predict` returns 503**: the model isn't installed - run
  `python installer/setup_wizard.py --skip-venv --model-dir <path>`.
